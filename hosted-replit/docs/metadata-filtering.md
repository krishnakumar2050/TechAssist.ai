# Metadata-scoped retrieval and RAG-Fusion

Per-request/turn/variant/channel correlation and policy fingerprints are
documented in [request-correlation.md](request-correlation.md).

## Policy and defaults

Every retrieval turn builds one immutable policy from **explicit employee
device context** and validated server configuration. OS can be confirmed by
the existing triage answers or device panel. The panel now also offers optional
device-type and manufacturer selections. Clearing them removes confirmation;
the free-text model field does **not** infer a vendor or create a model match.
New fields persist in existing conversation JSON; no SQL migration is needed.

Generated query variants never build, modify or receive authority over filters.
The same policy and provider predicate are shared by every dense/lexical branch.
Namespace, ready-document status and embedding compatibility remain mandatory.
Authentication, administrator authorization and owner-scoped conversations remain
separate: metadata is evidence scope, **not employee access control**.

Default behavior:

- Match confirmed OS family and Windows version. Windows 10 never borrows
  Windows 11 evidence. Unversioned Windows procedures are not assumed compatible
  with a confirmed version; an employee who supplies only "Windows" is asked
  which version before retrieval.
- Normalize the current platform strings and explicit legacy `os` aliases.
  Conflicting aliases or unrecognized/missing platform metadata are excluded,
  not treated as general. Explicit `general`, `all`, `all platforms`,
  `os-agnostic` and `cross-platform` declare genuinely general scope.
- `Dell laptops` means general-OS **Dell laptop** scope, not general hardware
  for any vendor. `Dell laptops with Windows` also requires Windows compatibility.
  `macOS; Mac laptops` declares Apple laptop scope. These mappings are explicit
  metadata aliases, not text heuristics. Current Ubuntu "desktop" strings describe
  OS scope; device type comes from `device_type`, not the word "desktop" in that
  platform label.
- Vendor-scoped evidence requires a matching confirmed manufacturer; generic
  vendor-independent evidence remains available. Dedicated legacy vendor fields
  accept only exact supported vendor names. Unsupported model-specific metadata
  is excluded rather than pretending to match a free-text employee model.
- A confirmed device type excludes mismatches. Missing device metadata is
  excluded when device type is constrained, unless a supported explicit
  platform alias declares it. Explicit general/all device scope is retained.
- With employee OS missing, OS-specific evidence is excluded; genuinely general
  evidence can remain. Existing Wi-Fi OS-then-symptom clarification still runs
  before searches. If evidence remains insufficient, ask for OS or explain the
  scope/coverage gap and offer handoff. Confirmed constraints are never relaxed.
- No default category, subcategory, language or review-age restriction.
- **No risk exclusion:** high-risk battery safety guidance is not removed merely
  because `risk_level=high`.
- `technical_validation=not_lab_tested` remains editorial provenance, never
  technician approval. Answer instructions explicitly prohibit approval/testing
  claims; Wi-Fi explanations identify editorial rather than lab-tested guidance.
- Review dates have no filtering effect unless explicitly configured below.

Legacy embedding-model aliases (`embeddingModel`, `embed_model`,
`embedding_model_name`), provider aliases and dimension aliases are recognized.
Model must match the approved Pinecone embedding model (optionally prefixed
`pinecone/`); incompatible provider/dimensions are rejected. Missing optional
legacy provider/dimension declarations do not override the source validation's
actual vector/index checks. Missing embedding model fails closed.

## Trusted optional configuration

`RAG_METADATA_FILTERS` is an optional **server-only JSON environment variable**,
default `{}`. It is not generated by Nebius or accepted as a chat/context
property. Unsupported keys, values, empty lists, invalid dates and conflicting
employee/configured device scopes fail explicitly rather than widening:

```json
{
  "category": ["software"],
  "subcategory": ["networking"],
  "language": ["en"]
}
```

All keys are optional; combine only those intended for the application:

| Key | Allowlist |
|---|---|
| `category` | `hardware`, `software` |
| `subcategory` | audio, battery_safety, bluetooth, bluetooth_audio, camera, camera_permissions, charging, cooling, crashes, disk_encryption, display, filesystem, graphics_driver, input_devices, mac_startup, memory, motherboard, networking, os_recovery, security, storage, updates |
| `language` | `en`, `es`, `fr`, `de`, `ja`, `zh` |
| `deviceType` | `laptop`, `desktop`, `tablet` |
| `vendor` | `dell`, `apple`, `hp`, `lenovo`, `asus`, `acer`, `microsoft`, `other` |
| `reviewedAfter` | Valid inclusive ISO date `YYYY-MM-DD` |

Category/subcategory/language take nonempty arrays (OR within a field, AND
between fields). Missing metadata fails an enabled constraint. Allowlisted
languages other than `en` currently produce zero matches, not an English fallback.
Device/manufacturer constraints intersect confirmed context; conflicts return
400. Invalid server configuration returns a safe 500 configuration error.

The generated OpenAPI context contract declares the optional device fields.
Routes additionally use strict generated Zod objects to reject unknown context
properties rather than silently stripping unsupported filter input.

## Verified Documents API and bounded compatibility strategy

Official contract consulted:
https://docs.pinecone.io/reference/api/2026-07/data-plane/search_documents

API `2026-07` uses **`filter`** alongside `score_by`, `top_k` and `include_fields`.
The official examples document `$and`, `$eq` and metadata comparison clauses;
live checks additionally confirmed `$or` and `$in`. Metadata fields not declared
in this index's schema are filterable. Only `embedding` and `text` are declared
schema fields; no normalized OS/vendor fields were written to the source.

```json
{
  "filter": {
    "$and": [
      {"language": {"$eq": "en"}},
      {"category": {"$in": ["hardware"]}}
    ]
  }
}
```

The normalized policy cannot be sent as fictitious `os_family`/`vendor` fields.
Instead, the compatibility strategy is explicit and bounded:

1. Read at most **513** ready, namespace/model-compatible local chunk IDs and
   metadata. More than **512** fails with 503, never silently truncates.
2. Evaluate normalized policy on this synchronized catalog and compile raw
   source metadata conjunctions for eligible records (including stable original
   document-identity aliases, platform aliases, device/category/language and
   embedding provenance). Combine distinct conjunctions with `$or`. Never use
   reserved `_id` as a metadata identity predicate. Empty scope short-circuits
   with zero retrieval calls, not an empty/unfiltered provider expression.
3. Send this predicate to **Documents API search before provider ranking**.
   Filter payloads above **128 KiB** fail closed. No failed-filter retry removes
   the predicate.
4. Request up to `max(40, catalog size)` dense candidates, bounded to 512.
   Intersect returned stable chunk IDs with the eligible catalog **before**
   the existing 40-per-branch/RRF budget. This accommodates aliases and missing
   optional legacy fields without destructive source normalization or ranking
   starvation within the synchronized small corpus.
5. PostgreSQL lexical search uses the same eligible IDs through parameterized
   `c.id=ANY($5::text[])` **before its ORDER BY/LIMIT 40**, in addition to existing
   namespace/status/model, lexical and Wi-Fi-anchor predicates.
6. RRF remains constant 60, deduplicated, with a combined maximum of 24.
   Recheck canonical metadata after mapping, then existing topic/symptom
   applicability before original-query neural reranking and citation generation.
   At most five evidence chunks; default relevance threshold remains **0.1**.

The local catalog is authoritative for application availability/status;
Pinecone has no application-owned `ready` field. New/unknown provider IDs cause
a synchronization service error, not a silent widening. Original Pinecone
vectors, records, metadata and IDs are never changed.

Partial dense/filter failures can retain successful **still-filtered SQL**
results, with failed-branch diagnostics. Total retrieval failure remains 503,
not a corpus gap. Larger corpora require a different verified mapping/filter
strategy before increasing this bound; this is not an unlimited corpus scan.

## Diagnostics and measured verification

`rag_metadata` logs only policy **key names**, catalog/eligible counts,
enumerated rejection counts, compatibility mode and clause count.
`rag_fusion` adds provider-returned and scope-rejected dense counts plus policy
keys. Final applicability logs metadata rejections. Never log policy values,
query/variant text, record IDs, source text, credentials, provider error bodies
or employee/conversation identifiers.
